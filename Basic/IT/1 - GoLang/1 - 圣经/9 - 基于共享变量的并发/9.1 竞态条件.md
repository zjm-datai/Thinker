
如果程序里只有一个执行流程（单个goroutine），那代码就按写的顺序一步步走，先执行第一句，再第二句，清清楚楚。

- 但如果程序里有多个执行流程（多个goroutine），每个流程内部的代码还是按顺序执行的。但**不同流程里的代码谁先谁后就说不准了**。 

比如： 

- 第一个 goroutine 里有个操作 x 
- 第二个 goroutine 里有个操作 y 

这时候 x 和 y 到底是x先执行、y 先执行，还是差不多同时执行，没法确定。这种情况就叫 x 和 y 是“并发”的。

考虑一下，一个函数在线性程序中可以正确工作，如果在并发的情况下，这个函数依然可以正确的工作的话，那么我们就说这个函数是并发安全的，并发安全的函数不需要额外的同步工作。我们可以把这个概念概括成为一个特定类型的一些方法和操作函数，对于某个类型来说，如果其所有可访问的方法和操作都是并发安全的话，那么该类型便是并发安全的。

就算程序里面使用了不能多线程同时使用的类型（非并发安全类型），也可以让整个程序做到多线程同时跑也不出问题（并发安全）。

其实，“能多线程同时用” 的类型（并发安全类型）是少数，大部分类型都不行。所以**除非文档明说某个类型能多线程同时用，否则千万别这么干**。

那怎么避免出问题呢？要么就让变量只在一个线程里用，要么就用锁之类的工具控制访问，保证同一时间只有一个线程能用它。这些办法我们后面会具体讲。

竞争条件指的是程序在多个 goroutine 交叉执行操作时，没有给出正确的结果。竞争条件是很恶劣的一种场景，因为这种问题会一直潜伏在你的程序里，然后在非常少见的时候蹦出来，或许只是会在很大的负载时才会发生，又或许是会在使用了某一个编译器、某一种平台或者某一种架构的时候才会出现。这些使得竞争条件带来的问题非常难以复现而且难以分析诊断。

传统上经常用经济损失来为竞争条件做比喻，所以我们来看一个简单的银行账户程序。

```go
package bank

var balance int

func Deposit(amount int) {
	balance = balance + amount
}

func Balance() int {
	return balance
}
```

对于这个简单的程序来说，我们一眼就可以看出来，用任意顺序调用函数 Deposit 和 Balance 都会得到正确的结果。也就是说，Balance 函数会给出之前的所有存入的额度之和。然而，当我们并发地而不是顺序地调用这些函数的话，Balance 就再也没办法保证结果正确了。考虑一下下面的两个 goroutine，其代表了一个银行联合账户的两笔交易：

```go
// Alice:
go func() {
    bank.Deposit(200)                // A1
    fmt.Println("=", bank.Balance()) // A2
}()

// Bob:
go bank.Deposit(100)                 // B
```

在这个例子中

- Alice 存 200 元，然后查余额
- Bob 同时存 100 元

假设初始余额是 0，Alice 要存 200，Bob 要存 100。

正常情况下，Alice 的存款（A1）应该是：

1. 读当前余额：0
2. 计算新余额：0 + 200 = 200
3. 写回新余额：余额变成 200

Bob 的存款（B）应该是：

1. 读当前余额：0（或 200，取决于顺序）
2. 计算新余额：0 + 100 = 100（或 200 + 100 = 300）
3. 写回新余额：余额变成 100（或 300）

但并发时可能出现这样的顺序：

1. Alice 先执行 “读余额”：读到 0，计划写 200（但还没写）。
2. **Bob 插队**：执行完整存款操作 —— 读 0 → 算 100 → 写回 100（此时余额实际是 100）。
3. Alice 继续执行 “写余额”：她之前算好的是 200，不管现在余额已经是 100，直接把 200 写回去。

最终余额变成 200，Bob 的 100 元就这样被覆盖了。

更严重的是，如果操作的是复杂类型（如切片、字符串等），可能会出现内存混乱，程序行为变得不可预测。

## 避免数据竞争的方法

### 不使用需要修改的变量

看看下面这个 map，它采用 "懒加载" 方式填充 —— 只有当某个 key 首次被访问时，才会为其赋值。如果 Icon 函数是被顺序调用的，程序可以正常工作；但如果有多个 goroutine 并发调用 Icon，这个 map 就会出现数据竞争问题：

```go
var icons = make(map[string]image.Image)
func loadIcon(name string) image.Image

// 注意：此函数不是并发安全的！
func Icon(name string) image.Image {
    icon, ok := icons[name]
    if !ok {
        // 首次访问，加载图标
        icon = loadIcon(name)
        icons[name] = icon  // 这里存在并发写入风险
    }
    return icon
}
```

相反，如果我们在创建 goroutine 之前的初始化阶段，就把 map 中的所有条目都初始化好，并且之后不再修改它们，那么即使有任意多个 goroutine 并发访问 Icon 函数也是安全的 —— 因为所有 goroutine 都只是读取操作：

```go
// 在初始化阶段就加载好所有图标
var icons = map[string]image.Image{
    "spades.png":   loadIcon("spades.png"),
    "hearts.png":   loadIcon("hearts.png"),
    "diamonds.png": loadIcon("diamonds.png"),
    "clubs.png":    loadIcon("clubs.png"),
}

// 此版本是并发安全的
func Icon(name string) image.Image { 
    return icons[name] 
}
```

在上面的例子中，icons 变量在包的初始化阶段就完成了赋值。包的初始化过程会在程序的 main 函数开始执行之前完成，而且一旦初始化完成，icons 就再也不会被修改。

### 避免多个 goroutine 访问同一个变量

例如，在之前的并发 web 爬虫（§8.6）中，只有 main goroutine 能够访问 seen map；聊天服务器（§8.10）中，也只有 broadcaster goroutine 能访问 clients map。这些变量都被严格限制在单个 goroutine 中。

由于其他 goroutine 无法直接访问这些变量，它们只能通过 channel 发送请求，由指定的 goroutine 来处理变量的查询和更新。这正体现了 Go 语言的口头禅："不要使用共享数据来通信，而要通过通信来共享数据"。

专门通过 channel 处理对某个变量的访问请求的 goroutine，被称为该变量的 "监控 goroutine"（monitor）。例如前面提到的 broadcaster goroutine，就负责监控对 clients map 的所有访问。

下面是一个重构后的银行账户示例，其中 balance 变量被限制在名为 teller 的监控 goroutine 中：

```go
// Package bank 提供了一个支持并发安全的银行账户实现
package bank

var deposits = make(chan int)  // 用于发送存款金额
var balances = make(chan int)  // 用于接收账户余额

// Deposit 向账户中存入指定金额
func Deposit(amount int) { deposits <- amount }

// Balance 查询当前账户余额
func Balance() int { return <-balances }

// teller 是监控 goroutine，负责维护账户余额
func teller() {
    var balance int  // balance 仅由 teller goroutine 访问
    for {
        select {
        case amount := <-deposits:
            balance += amount  // 处理存款
        case balances <- balance:  // 响应余额查询
        }
    }
}

// 初始化时启动监控 goroutine
func init() {
    go teller()
}
```

即使变量无法在整个生命周期中都绑定到单个 goroutine，"绑定" 依然是解决并发问题的有效方案。

例如，在流水线（pipeline）模式中，goroutine 之间通过 channel 传递变量地址是很常见的。如果流水线的每个阶段在将变量传递到下一阶段后，就不再访问该变量，那么对这个变量的所有访问就是线性的。其效果是变量先被绑定到流水线的一个阶段，传递后再绑定到下一个阶段，依此类推。这种规则称为 "串行绑定"。

下面的例子中，Cake 实例会被严格顺序访问：先由 baker goroutine 处理，再由 icer goroutine 处理：

```go
type Cake struct{ state string }

// baker 制作蛋糕并发送到下一流水线
// cooked 是只发送通道，只能往里面发送 *Cake 类型的数据
func baker(cooked chan<- *Cake) {
    for {
        cake := new(Cake)
        cake.state = "cooked"
        cooked <- cake  // 发送后，baker 不再访问这个蛋糕
    }
}

// icer 接收烘焙好的蛋糕，进行上霜处理后发送到下一流水线
func icer(iced chan<- *Cake, cooked <-chan *Cake) {
    for cake := range cooked {
        cake.state = "iced"
        iced <- cake  // 发送后，icer 不再访问这个蛋糕
    }
}
```
