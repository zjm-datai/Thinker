SSE 是单向的，这意味着：

- 方向固定：只能通过服务端向客户端进行数据推送
- 客户端不能通过这条 SEE 长连接反向发送数据给服务端

## 什么是长连接？

在网络通信中，长连接时指客户端和服务器建立连接之后，不会立即断开，而是保持连接状态，以便双方在一段时间内持续进行数据交互的通信方式。与之对应的是短连接，每次通信完成之后立即断开连接。

### 长连接的核心特点

1. **连接持续性**  
    一旦建立连接，除非发生异常（如网络中断、超时、手动关闭等），否则连接会一直保持。客户端和服务器可以随时通过该连接发送数据，无需重复建立连接。

2. **减少连接开销**  
    避免了频繁建立和关闭连接的过程（如 TCP 的三次握手、四次挥手），节省了网络资源和时间，尤其适合需要频繁交互的场景。

3. **心跳机制维护**  
    为防止连接因长时间无数据传输而被中间节点（如路由器、防火墙）断开，长连接通常会通过 “心跳包”（定期发送的小数据包）维持活性，证明连接仍然有效。

### 长连接的典型应用场景

- **即时通信**：如微信、QQ 等聊天软件，需要实时接收消息，长连接能确保消息快速传递。
- **在线游戏**：玩家操作和游戏状态需要实时同步，长连接可减少延迟。
- **实时数据推送**：如股票行情、监控数据更新等，服务器需主动向客户端推送实时信息。
- **WebSocket 协议**：基于 TCP 的全双工通信协议，本质上是对长连接的优化（通过一次握手建立持久连接，支持双向实时数据传输）。

**SSE（Server-Sent Events，服务器发送事件）** 是长连接的典型应用之一，它基于 HTTP 协议实现了服务器向客户端的单向持续数据推送。

SSE 的核心机制是：

1. 客户端与服务器建立一次 HTTP 连接后保持该连接不关闭（长连接特性）
2. 服务器可以随时通过这个长连接向客户端推送数据
3. 数据以特定格式（`text/event-stream`）持续发送，客户端通过事件监听处理这些数据

与 WebSocket 的全双工通信不同，SSE 是**单向通信**（仅服务器向客户端发送），但实现更简单，无需专门的协议升级，完全基于 HTTP，适合新闻推送、实时通知、数据监控等场景。

SSE 本质上是对 HTTP 长连接的一种优化利用，通过保持连接状态实现高效的持续数据传输，因此属于长连接的典型应用范畴。

## 什么是单向

在网络通信里，如果一条连接允许数据双向传输（比如 WebSocket），那叫**双向（full-duplex）**；  
如果只能一方发数据、另一方只能收，那就是**单向（half-duplex 或 unidirectional）**。

SSE 的情况是这样的：

```
客户端（浏览器） 发起 HTTP GET 请求  ---->
服务端：发送 HTTP 响应（Content-Type: text/event-stream） -->
服务端：持续往响应里写事件（event: ...\ndata: ...）
服务端：持续推送...
客户端：只能接收，不能在这条流里发数据
```

客户端要给服务端发东西，只能**重新开一个新的 HTTP 请求**（短连接），而不能复用 SSE 这条长连接。

#### 什么是 HTTP

**HTTP（Hypertext Transfer Protocol，超文本传输协议）** 是一种用于在网络上传输数据的规范，是互联网的基础协议之一，主要用于客户端（如浏览器）与服务器之间的通信。

简单来说，HTTP 定义了客户端如何向服务器请求资源（如网页、图片、数据等），以及服务器如何响应这些请求的规则。

## 为什么 SSE 是单向的

- **技术原因**：SSE 是基于 HTTP 的响应流（Response stream），客户端发起请求后，HTTP 响应一旦开始，就只能由服务器往客户端写数据，客户端不能再往这个响应里加内容。
    
- **设计目的**：SSE 诞生就是为了“服务器定期或实时推送数据给浏览器”，不是为了双向通信。
    
- 如果需要双向，通常用 **WebSocket**。

| 特性    | SSE                 | WebSocket        |
| ----- | ------------------- | ---------------- |
| 数据方向  | 单向（Server → Client） | 双向               |
| 协议    | HTTP (基于响应流)        | 独立协议（ws://）      |
| 浏览器支持 | 原生 EventSource API  | 原生 WebSocket API |
| 自动重连  | 内置                  | 需自己实现            |
| 消息格式  | 文本（UTF-8）           | 文本 / 二进制         |

## 具体实现

SSE（Server-Sent Events）其实既可以说是**一种协议**，也可以说是一种**技术/机制**，但它在标准里的定位更接近 **“基于 HTTP 的传输协议规范”**。

### 从协议角度看

- SSE 是 **HTML5 标准** 里定义的一个数据传输机制，详细规范在 WHATWG HTML Living Standard 中。

- 它规定了：
    
    1. **HTTP 请求/响应的格式**（`Content-Type: text/event-stream`）
        
    2. **数据流格式**（`event:`、`data:`、`id:` 等字段）
        
    3. **客户端行为**（如何处理断线、重连）

- 所以它确实是一个**标准化的通信协议**，而且是**单向的、基于 HTTP 的事件流协议**。

### 从技术实现角度看

- 实现 SSE 不需要额外的独立 TCP 协议，它完全运行在 **HTTP/1.1 或 HTTP/2** 上。

- 技术上就是：
    
    1. 客户端发一个普通的 HTTP GET 请求。
        
    2. 服务器返回一个特殊类型的响应（text/event-stream）。
        
    3. 服务器保持响应**不关闭**，持续不断地往里面写数据。
        
    4. 浏览器用 EventSource API 自动解析这些数据，并触发事件回调。

## 常见问题

他比 websocket 这种长连接好在哪里，是不是不同服务器实现 sse 的逻辑可以不同，只要满足一定的特性就可以了？

### SSE 相比 WebSocket 的优势

**更简单的实现**

- SSE 时标准的 HTTP 响应流（Content-Type: text/event-stream），在 HTTP/1.1、HTTP/2 上直接跑，不需要额外的握手协议。

- 服务端只要能返回一个保持打开的 HTTP 响应流，就能做 SSE。

- WebSocket 则需要额外的握手升级（Upgrade: websocket），以及在应用层自己定义消息格式、心跳机制等。

**浏览器原生支持**

- `EventSource` API 在现代浏览器里直接用，不需要引入额外 JS 库。
    
- WebSocket 也有原生 API，但它是双向的，意味着要处理更多逻辑。
    

**天然支持 HTTP 特性**

- SSE 可以直接利用 HTTP 缓存头、Cookie、认证机制、代理、负载均衡。
    
- WebSocket 在进入二进制协议后，就得自己处理认证、心跳、断线重连。

**内置自动重连**

- SSE 客户端断线时，浏览器会自动重连，并且可以用 Last-Event-ID 从上次中断的位置继续。
    
- WebSocket 需要自己实现断线重连和消息补发逻辑。

**更容易穿透网络限制**

- SSE 用的就是标准 HTTP/HTTPS 端口（80/443），不会被严格的企业防火墙轻易拦掉。
    
- WebSocket 有时在代理/防火墙后面会遇到兼容问题。

### 关于“不同服务器实现 SSE 的逻辑是否不同”

**SSE 不是一种具体的库或框架**，而是一份标准协议规范（HTML5 标准的一部分）。  

所以：

- 不同服务器框架（FastAPI、Express、Spring Boot、Go net/http）实现 SSE 的方式可以不同。
    
- 但只要满足**协议的几个核心特性**，客户端就能正常用 EventSource 接收：
    
    1. HTTP 响应头 Content-Type: text/event-stream
        
    2. 响应不关闭（保持长连接）
        
    3. 按 SSE 格式推送数据：

```
data: 消息内容\n
\n
```

4. 服务端保证按行分隔事件，并正确处理重连（Last-Event-ID）

### 总结一句话

- **SSE 适合单向推送场景**：实现简单、浏览器支持好、用 HTTP 生态的好处多。

- **WebSocket 适合双向通信**：灵活、功能全，但实现复杂度和维护成本更高。

- 不同服务器实现 SSE 的细节可以不同，只要遵循协议特性，客户端就能收得到。
