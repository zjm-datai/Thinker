
**列最小、主键完整、不跨列传递**

三大范式是对数据库设计的分级规范：

1. 保证字段是最小单位
2. 保证非主属性完全依赖主键
3. 保证非主属性之间没有传递依赖

关系型数据库的三大范式 3NF 的基础概念，用于设计数据库表结构时候的规范，目的是为了减少冗余，提高数据一致性。

## 第一范式：列不可再分

表示每一列都必须是原子值，也就是不可再分割的最小单位

### 常见的违反场景

将多个值塞到一个字段（爱好字段存成 “篮球，足球，游泳”）

使用 JSON，CSV，数值之类非原子的复合数据类型（除非我们的关系型数据库原生支持，且必须要这么干）

## 第二范式：行可以唯一区分，主键约束

建立在第一范式基础上，要求**表中的每个非主属性完全依赖主键**。表必须有主键，非主键字段必须完全依赖主键，而不能只依赖主键的一部分（适用于复合主键的情况）。

假设有一个成绩表：

| 学号  | 课程号 | 学生姓名 | 课程名称 | 成绩  |
| --- | --- | ---- | ---- | --- |

主键是学号和课程号，联合主键

成绩是依赖于学号和课程号的，这是可以的。但是学生姓名只依赖于学号，不好。课程名称只依赖课程号，所以这表不满足第二范式。所以这张表应该拆分成两个表：

学生表（学号，学生姓名）课程表（课程号, 课程名称）成绩表（学号, 课程号, 成绩）

## 第三范式：消除 “传递依赖”

表的非主元素不能依赖于其他表的非主属性，建立在 1NF 和 2NF 基础上，要求**非主属性之间不能存在传递依赖**。

|员工编号|部门编号|部门名称|
|---|---|---|

员工编号是主键，部门名称依赖于部门编号，但部门编号又是非主属性

所以 部门名称 是**通过部门编号间接依赖主键**，违反了 3NF。

正确做法是：员工表（员工编号, 部门编号）部门表（部门编号, 部门名称）

三大范式是一级一级依赖的，第二范式建立在第一范式上，第三范式建立在第一第二范式上。

**主键约束**：确保一张表中每一行的唯一性，标志该行的身份。

**外键约束**：用于建立表与表之间的联系，确保引用的数据存在于父表中（如员工表中的部门编号必须存在于部门表中）。

## 范式化和反范式化

范式化的优点在于：

- 消除冗余，更新异常 update anomaly，插入异常，删除异常
- 节省存储，数据一致性高

### 反范式化场景

高并发查询需要减少 JOIN 

统计、报表系统，预先冗余计算结果

分布式场景下需要宽表或物化视图

### 实务口诀

先范式后反范式，先严格 3NF，再按性能可控的放宽

## 实战案例

需求：

- 一个订单可含多个商品，一个商品可出现于多个订单。
    
- 记录商品单价、数量、折扣。
    
- 记录客户、收货地址、下单时间。

1. 初始“一张大表”

```
OrderAll(
    order_id,
    customer_id,
    customer_name,
    customer_phone,
    customer_addr,
    product_id,
    product_name,
    product_price,
    qty,
    discount,
    order_time
)
```

问题：

- 客户信息、商品信息重复存储 → 冗余。
    
- 更新客户电话需要改多行 → 更新异常。
    
- 删除最后一个订单行会把客户信息也删掉 → 删除异常。

2. 范式化到 3NF

```
Customer(customer_id PK, customer_name, customer_phone, customer_addr)
Product(product_id PK, product_name, product_price)
Orders(order_id PK, customer_id FK, order_time)
OrderItem(
    order_id FK,
    product_id FK,
    qty,
    discount,
    PRIMARY KEY(order_id, product_id)
)
```

- 所有非主属性都只依赖于各自表的主键，无部分依赖、无传递依赖。
- 连接表 OrderItem 用复合主键，避免额外代理键（节省索引）。

3. 反范式微调（可选）

- 如果订单详情查询量极高，可把 `product_name, product_price` 冗余到 OrderItem，减少一次 JOIN。

- 用触发器或 CDC 保证冗余字段同步。
