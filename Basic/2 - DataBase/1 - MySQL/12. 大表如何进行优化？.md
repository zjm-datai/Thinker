
当 MySQL 单表记录数过大的时候，数据库的 curd 性能会明显下降，一些常见的优化措施如下：

### 限定数据的范围

务必禁止不带任何限制数据范围条件的查询语句，比如：我们当用户在查询订单历史的时候，我们可以控制在一个月的范围内。

### 读写分离

经典的数据库拆分方案，主库负责写，从库负责读。

读写分离把大表的高并发读流量从主库挪到 N 台从库，让主库专心写，从而间接让大表的读性能看起来提升了 N 倍，而不用先去做更贵的分库分表。

| 场景        | 没读写分离                                                | 有读写分离                        | 读大表是否受益 |
| :-------- | :--------------------------------------------------- | :--------------------------- | :------ |
| **报表/BI** | 一条 `SELECT COUNT(*) FROM orders` 把主库 CPU 打满，线上订单写不进去 | 同样 SQL 丢给 3 台从库并行跑，主库无感知     | 直接受益    |
| **活动秒杀**  | 商品详情页 QPS 2 万，全砸在主库，行锁/页锁拖死写操作                       | 2 万读 QPS 分散到 4 台从库，主库只剩下单写   | 直接受益    |
| **分页搜索**  | 模糊 LIKE 走大表索引失效，主库 I/O 100%，用户下单超时                   | 把慢 SQL 路由到只读从库，主库 I/O 降回 20% | 直接受益    |

注意：它优化的不是“单条 SQL 对大表的扫描速度”

- 一条 `SELECT * FROM big_table WHERE id = 123` 在主库还是 5 ms，在从库也是 5 ms。**单条查询本身没更快**。
    
- 但当 10 000 个并发同一时刻都要跑这条 5 ms 的 SQL，主库可能被 I/O 或行锁拖垮，而从库可以水平扩展 10 台，每台只扛 1000 并发，**整体吞吐提高 10 倍** —— 这就是“读大表优化”的本质：**并发能力的横向扩容，而非单条 SQL 的性能提升**。

### 垂直分区

根据数据库里面的数据库的相关性进行拆分。例如，用户表中既有用户的登录信息又有用户的基本信息，可以将用户表拆分成两个单独的表，甚至放到单独的库做分库。

简单来说垂直拆分就是指数据表列的拆分，把一张列比较多的表进行拆分成多张表。
