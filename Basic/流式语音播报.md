
我们维护了一个 WebsocketTTS.vue 组件，这个组件可以做到流式音频接收和实时播放。他通过和 websocket 和服务端保持长连接，前端不断接收服务端推送的音频字节流；

这个组件会首先向客户端发送我们要的音色等 tts 生成配置，然后不断的从事件总线中拉取其他组件推送的文本流，然后推给 websocket 后端，最后在得到文本流结束的信号之后，给 websocket 发送 eof；

然后当 ws 开始发送音频字节流回来的时候，一开始是会发送 start 信号过来，里面是本次生成音频字节的信息，然后我们会根据这个信号来判断编码格式后再进入对应播放链路；

对于压缩格式比如 mp3 或者是 ogg，组件会利用 Mediasource Extension MSE 在浏览器端动态追加音频片段到 sourceBuffer，让 `<audio>` 标签像播放网络流一样边下边播；

对于原始 PCM 流，则利用 WebAudioAPI 创建 AudioContext ，把每一帧 Int16 数据实时转换为 Float32，生成 AudioBuffer 并按照时间戳排入播放队列，借助 currentTime 和自维护的时间光标 timeCursor 保持连续无缝播放；

这样，前端无需等待完整文件生成，而是能做到低延迟、边接收边合成边播报，实现真正的流式 TTS 播报体验。

```ts
ws.onmessage = (evt) => {
    if (typeof evt.data === 'string') {
      try {
        const msg = JSON.parse(evt.data);
        if (msg.type === 'start') {
          haveStart = true;
          const fmt = String(msg.format || props.format || '').toLowerCase();
          const mime = String(msg.mime || '').toLowerCase();
          const sr   = Number(msg.sample_rate || props.sampleRate || 24000);

          console.log("msg: ", msg);

          if (fmt === 'wav') { // 按你后端逻辑，wav 会转成 pcm
            handleStartPCM(sr);
          } else if (fmt === 'pcm') {
            handleStartPCM(sr);
          } else if (fmt === 'mp3') {
            handleStartMP3(mime || 'audio/mpeg');
          } else {
            // 其它格式按 mp3 处理（大多也是压缩容器）
            handleStartMP3(mime || 'audio/mpeg');
          }

          // 把 preStartBin（若有）按对应路径处理，在 start 之前如果有莫名其妙传来的字节
          // 由于 websocket 是乱序到达的，所以可能有这种情况
          // 我也很纳闷，其实我们后端的 ws 逻辑应该是顺序的，可能是网络层面的乱序？
          if (preStartBin.length) {
            const tmp = preStartBin.splice(0, preStartBin.length);
            for (const c of tmp) {
              if (isPCM()) playPcmChunk(c);
              else appendMp3(c);
            }
          }

        } else if (msg.type === 'end') {
          ending = true;
          if (!isPCM() && mediaSource?.readyState === 'open') {
            flushMp3Queue();
            try { mediaSource.endOfStream(); } catch {}
          }
        } else if (msg.type === 'ping') {
          // ignore
        } else if (msg.type === 'error') {
          console.error('[WebsocketTTS] server error:', msg.message);
        }
      } catch {
        // 非 JSON 文本帧（极少），忽略
      }
    } else {
      // 上述情况优先级比处理音频消息高~
      const u8 = new Uint8Array(evt.data as ArrayBuffer);
      if (!haveStart) {
        preStartBin.push(u8);
      } else {
        if (isPCM()) {
          console.log("is pcm audio")
          playPcmChunk(u8);
        }
        else appendMp3(u8);
      }
    }
  };
  ws.onerror = (e) => console.info('[WebsocketTTS] ws error', e);
}
```

### 专有名词解释

WebSocket：这是一种全双工的持久连接协议，前端和服务端可以实时互相推送消息。这里用它来让服务端源源不断地把音频字节流推过来，而前端也能不断把增量的文本推过去。

PCM（Pulse Code Modulation，脉冲编码调制）：它就是最原始的音频采样格式，可以理解为麦克风采样得到的音频波形值。通常是 16 位整型，一个个数值代表波形幅度。它的好处是解码简单，不需要再解压缩，但缺点是数据量大。

AudioContext 是 Web Audio API 的核心对象，可以理解成浏览器里面专门负责音频信号处理和播放的一个音频引擎。

当我们 new 一个 AudioContext，其实就是在浏览器里面打开一条音频通道，它内部有一个时间线 currentTime，所有声音的播放，合成，滤波，音量调节都会挂在这条时间线上。

在这个上下文里，你可以创建各种“音频节点”（比如音量控制的 GainNode、缓冲区的 AudioBufferSourceNode），这些节点像电路里的模块一样，用 connect() 串联起来，最后连到 destination（扬声器/耳机）。

在我们这个 TTS 播报场景里：服务端传过来的 PCM 数据就是一堆原始采样点。我们先把它转成 Float32Array，再塞进 AudioBuffer，然后交给 AudioBufferSourceNode。再把这个节点 connect 到 GainNode（音量控制），最后 connect 到 AudioContext.destination。

播放的时候，我们用 AudioContext.currentTime 加上一个自维护的 timeCursor 来决定何时 start()，确保连续的缓冲不会断裂或重叠，从而实现无缝衔接。

AudioContext 就是浏览器里的音频工作室，你在里面排布节点、放入音频数据，浏览器就会按时间线把声音准确输出到设备。

MSE（MediaSource Extensions）：这是浏览器提供的一种接口，允许开发者动态地往 `<audio>` 或 `<video>` 里追加媒体片段，就像自己在“拼”一个媒体流。适合用来播放 MP3、OGG 这种压缩格式，因为浏览器本身已经能解码这些压缩音频，只要你不断把字节流 append 到 SourceBuffer，播放器就会一边解码一边播放。

为什么要分两条路径：

- 如果服务端输出的是 PCM，这时不能直接塞给 `<audio>`，因为它只认标准编码格式（mp3、ogg、wav…），所以必须用 Web Audio API 逐帧还原并播放。
- 如果服务端输出的是 MP3/OGG，这些浏览器本身就支持解码，那最简单高效的方式就是用 MSE 把片段拼接进 `<audio>`，省去我们自己转码。
