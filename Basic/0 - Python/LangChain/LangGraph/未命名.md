### 状态（State）

定义图的时候，第一件事就是确定图的“状态”。这个状态由两部分组成：一是图的结构蓝图（schema），二是 reducer 函数——它们负责规定如何根据更新来修改状态。状态的结构蓝图会成为图中所有节点（Nodes）和边（Edges）的输入格式，可以用 TypedDict 或者 Pydantic 模型来定义。所有节点都会输出状态的更新，然后这些更新会通过指定的 reducer 函数应用到状态上。


### 结构蓝图（Schema）

目前官方推荐的定义图结构蓝图的方式是用 TypedDict。如果想给状态设置默认值，那就用 dataclass。要是你需要递归的数据验证，也可以用 Pydantic 的 BaseModel 作为图的状态——不过要注意，Pydantic 的性能可比 TypedDict 或 dataclass 差一些哦。

默认情况下，图的输入和输出会用同一个结构蓝图。但如果你想分开设置也完全可以，直接指定专属的输入和输出蓝图就行。这招在状态里键很多，而且有些键只用于输入、有些只用于输出的时候特别好用。想知道具体怎么操作？


### 多蓝图玩法

通常来说，图里的所有节点都用同一个结构蓝图交流，也就是说它们读写的是同一个状态通道。但有时候我们想玩点花样：

- 内部节点之间想传递一些“悄悄话”，这些信息没必要出现在图的输入或输出里；
- 图的输入和输出想用不同的蓝图——比如输出可能只需要一个关键结果键。

这种时候，我们可以让节点在图的“私有状态通道”里写写画画，专门用来内部沟通。简单定义一个 PrivateState 蓝图就行。

另外，也可以给图明确定义输入和输出蓝图。这种情况下，我们会先定义一个“内部”蓝图，包含图运行所需的所有键；然后再把输入和输出蓝图设为内部蓝图的子集，这样就能限制图的输入和输出啦。

来看个例子感受下：

```python
class InputState(TypedDict):
    user_input: str  # 输入蓝图：只包含用户输入

class OutputState(TypedDict):
    graph_output: str  # 输出蓝图：只包含图的输出

class OverallState(TypedDict):
    foo: str
    user_input: str
    graph_output: str  # 内部蓝图：包含所有运行需要的键

class PrivateState(TypedDict):
    bar: str  # 私有蓝图：节点间的“悄悄话”通道

def node_1(state: InputState) -> OverallState:
    # 读取 InputState，写入 OverallState
    return {"foo": state["user_input"] + " name"}

def node_2(state: OverallState) -> PrivateState:
    # 读取 OverallState，写入 PrivateState
    return {"bar": state["foo"] + " is"}

def node_3(state: PrivateState) -> OutputState:
    # 读取 PrivateState，写入 OutputState
    return {"graph_output": state["bar"] + " Lance"}

# 用内部蓝图初始化图，同时指定输入和输出蓝图
builder = StateGraph(OverallState, input_schema=InputState, output_schema=OutputState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_node("node_3", node_3)
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
builder.add_edge("node_2", "node_3")
builder.add_edge("node_3", END)

graph = builder.compile()
graph.invoke({"user_input":"My"})  # 输出：{'graph_output': 'My name is Lance'}
```

这里有两个很巧妙的点要划重点：

1. node_1 的输入是 InputState 蓝图，但它却能往 OverallState 里的 foo 键写东西。这是因为节点可以写入图状态里的任何通道——图的状态是初始化时定义的所有通道的集合，包括 OverallState 以及 InputState、OutputState 这些“过滤器”哦。

2. 我们用 `StateGraph(OverallState, ...)` 初始化了图，但 node_2 却能往 PrivateState 里写 bar 键。这是因为只要定义了对应的蓝图（比如这里的 PrivateState），节点就可以声明新的状态通道，随心所欲地添加新键啦~


### Reducer 函数：状态更新的“调节器”

想搞懂节点的更新是怎么应用到状态上的，reducer 函数是关键！状态里的每个键都有自己独立的 reducer 函数。如果没明确指定，那默认就是“覆盖更新”——新值直接把旧值干掉。

reducer 有好几种类型，先从默认的说起：
#### 默认 Reducer

看两个例子就明白默认 reducer 咋工作的了：

**例子 A：纯默认模式**

```python
from typing_extensions import TypedDict

class State(TypedDict):
    foo: int
    bar: list[str]  # 没指定 reducer，默认用“覆盖更新”
```

假设图的初始输入是 `{"foo": 1, "bar": ["hi"]}`。第一个节点返回 `{"foo": 2}`（注意：节点不用返回整个状态，只返回要更新的部分就行）。应用这个更新后，状态会变成 `{"foo": 2, "bar": ["hi"]}`（bar 没被碰，保持原样）。

如果第二个节点返回 `{"bar": ["bye"]}`，那状态就会变成 `{"foo": 2, "bar": ["bye"]}`——bar 被新列表彻底覆盖啦。


**例子 B：给 bar 加个“累加器”**

```python
from typing import Annotated
from typing_extensions import TypedDict
from operator import add  # 引入加法函数

class State(TypedDict):
    foo: int  # 还是默认的覆盖更新
    bar: Annotated[list[str], add]  # 用 add 当 reducer：列表会累加
```

同样初始输入 `{"foo": 1, "bar": ["hi"]}`。第一个节点返回 `{"foo": 2}`，状态变成 `{"foo": 2, "bar": ["hi"]}`（和之前一样）。

但第二个节点返回 `{"bar": ["bye"]}` 时，神奇的事发生了！因为 bar 用了 add  reducer，所以会把新旧列表加起来，状态变成 `{"foo": 2, "bar": ["hi", "bye"]}`——是不是很像给列表开了“累加挂”~
