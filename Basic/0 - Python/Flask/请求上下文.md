
请求上下文会在请求过程中跟踪请求级别的数据。请求级别的数据在框架中的流动方式并不是一个函数一个函数的传递，而是通过维护 request 和 session 这两个 proxies ，然后各个函数通过访问他们得到请求上下文。

这与 [[应用程序上下文]] 类似，应用程序上下文会跟踪与请求无关的应用程序级数据。当请求上下文被推入时，相应的应用程序上下文也会被推入。

## 上下文的目的

当 Flask 应用程序处理请求时，它会根据从 WSGI 服务器接收到的环境创建一个Request 对象。 Because **a worker (thread, process, or coroutine depending on the server) handles only one request at a time**, the request data can be considered global to that worker during that request. Flask uses the term **context local** for this.

Flask 在处理请求时会自动推送一个请求上下文。在请求处理过程中运行的视图函数、错误处理程序和其他函数将能够访问 request proxy，该代理指向当前请求的请求对象。

## 请求的生命周期

当 Flask 应用程序开始处理请求时，它会推送一个请求上下文，这也会推送一个应用程序上下文。当请求结束时，它会弹出请求上下文，然后弹出应用程序上下文。

The context is unique to each thread (or other worker type). 请求不能被传递到另一个线程，因为另一个线程有不同的上下文空间，并且不会知道父线程所指向的请求。

Context local 是使用 [[Python 的 contextvars]] 和 [[Werkzeug 的 LocalProxy]] 实现的。Python 自动管理上下文变量的生命周期，而 Context local 则封装了底层接口，使数据更易于使用。

## Callbacks and Errors

Flask dispatches a request in multiple stages which can affect the request, response, and how errors are handled. The contexts are active during all of these stages.

蓝图可以为这些特定于蓝图的事件（add handlers for these event that are specific to the blueprint）添加处理程序。如果蓝图拥有与请求匹配的路由，则会运行该蓝图的处理程序。

1. 在每次请求之前，会调用 before_request() 函数。如果其中一个函数返回一个值，其他函数将被跳过。返回值将被视为响应，视图函数将不会被调用。

2. 如果 before_request() 函数没有返回响应，则会调用匹配路由的视图函数并返回一个响应。

3. 视图的返回值会被转换为实际的响应对象，并传递给 after_request() 函数。每个函数都会返回一个修改后的或新的响应对象。

4. 在返回响应后，上下文会被弹出，这会调用 teardown_request() 和 teardown_appcontext() 函数。即使在上述任何阶段引发了未处理的异常，也会调用这些函数。

If an exception is raised **before the teardown functions**, Flask tries to match it with an [[errorhandler function]] to handle the exception and return a response. 如果未找到错误处理程序（error handler），或者 the handler itself raises an exception 引发异常，Flask 将返回通用的 500 内部服务器错误响应。销毁函数（treardown functions）仍会被调用（called），并传入异常对象（passed the exception object）。

如果启用了调试模式，未处理的异常不会转换为 500 响应，而是会传播（propagated）到 WSGI 服务器。这使得开发服务器（development server）能够通过回溯信息展示交互式调试器（interactive debugger）。

### Teardown Callbacks

> Flask 中的 teardown 回调函数是在请求上下文结束时自动触发的，不管请求处理过程中有没有出错。这些函数和处理请求的主流程是分离的，所以你写 teardown 函数时，**不能假设请求处理已经完成或没有出错**，也**不能依赖其他回调函数是否执行过**。你要确保 teardown 函数本身足够稳健，能在任何情况下安全运行。

The teardown callbacks are independent of the request dispatch, and are instead called by the contexts when they are popped. 这些函数是在 **Flask 的上下文（比如应用上下文或请求上下文）被移除（popped）** 时自动调用的，而不是由你显式地调用。即使在处理请求时出现了 **未处理的异常 unhanlded exception**，teardown 回调函数 **仍然会被调用**。即使你手动推送了一个上下文（比如在单元测试或脚本中使用 `app.app_context()` 或 `app.test_request_context()`），只要上下文被移除，teardown 回调函数也会被执行。

由于 teardown 是在上下文被销毁时触发的，**你不能指望别的处理逻辑（比如请求处理函数、其他回调）一定已经执行过**。所以你要写得足够安全，不能依赖于其他部分是否已经执行。

我们在写 teardown 函数时要注意：**不要依赖其他回调是否被调用过**，也要保证函数本身 **不会因为某个状态缺失或异常而崩溃**。这里的其他回调是指 before_request 等一系列钩子方法。

我们可以举一个例子：

```python
@app.before_request
def setup():
    g.db = connect_to_database()

@app.teardown_request
def cleanup(exception):
    g.db.close()  # ⚠️ 你必须先判断 g.db 是否存在
```

这里写的就不好，如果 `before_request` 没执行成功，或者在它之前请求已经出错了，那么 `g.db` 可能根本没创建。如果你在 teardown 里 **直接用 `g.db.close()` 而不检查**，就可能抛出 `AttributeError`。

所以文档建议你 teardown 函数要写得 **健壮、安全，不依赖其他回调是否执行过**。

## 有关 Proxies 的一些细节

>Some of the objects provided by Flask are proxies to other objects. The proxies are accessed in the same way for each worker thread, but point to the unique object bound to each worker behind the scenes as described on this page.

在 Flask 中，一些对象其实是 **“代理对象（proxies）”**，它们背后实际上引用的是 **当前线程或上下文中的真实对象**。这些代理对象在不同线程中以相同的方式访问，但它们 **指向的实际对象是唯一的、与线程或请求上下文绑定的**，具体机制可以参考本页的详细解释。

🔹 大多数情况下你不需要关心这一点，Flask 已经为你封装好了。

但是在某些特定场景下，**了解它们是代理对象是很有用的**，因为会影响到你怎么使用它们。

有两个需要注意的地方：

### 代理对象不能伪装成真实对象的类型

- 也就是说，如果你使用 `isinstance(obj, SomeClass)` 去判断这个对象是否是某种类型时，在代理对象上通常 **返回 False**。

- 因为 Flask 的代理对象（比如 `current_app`, `request`, `g` 等）是 `werkzeug.local.LocalProxy` 类型的，而不是你要检查的那个类本身。


**怎么办？**  

需要先获取被代理的真实对象，然后再做类型判断。

### 有些情况需要使用真实对象的引用

例如：

- 当你要发送 **Flask 的 Signal（信号）**；

- 或者你想在一个 **后台线程（例如异步任务）** 中传递 Flask 上下文相关的对象（如 `current_app`）。

这时，代理对象无法满足需求，必须取出真实对象。

**怎么做？**  

使用 `._get_current_object()` 方法来获取被代理的真实对象。

```python
from flask import current_app

# 获取被代理的真实 app 实例
app = current_app._get_current_object()

# 使用真实对象发送 signal
my_signal.send(app)
```

### Flask 中常见的代理对象

|对象名|实际绑定对象（每个请求独立）|
|---|---|
|`current_app`|当前运行的 Flask 应用实例|
|`request`|当前请求对象（包含 headers、args 等）|
|`g`|当前请求的全局命名空间（可存储临时数据）|
|`session`|当前用户的 session 数据|

这些对象本身是“壳子”，真正的数据在幕后存放在一个“上下文栈”里，Flask 会根据当前线程/请求自动定位并提供正确的对象。
