### 开发计划

视频流的截断与恢复静默部分问题不大，原项目里已经实现了。  
接下来是 API 改造。这块估计不能只是把原本自部署模型的 handler，直接改成调用 API 的 handler。  
主要原因有两个：

1. ASR 模型涉及音频文件存储到 MinIO；
2. 对话接口可能不仅使用大模型的接口，还会用到 Dify 的接口。

理想的方案是：  
RTC 服务器只接收文本的流式输入；  
然后只负责管理 TTS 和 Avatar 视频两个 handler，向外传回音视频流。

---

1. 用户输入语音是有两个交互的，第一个是要和正常的后端 asr 服务沟通，先存 minio 然后得到文件地址请求 qwen-aduio 接口，第二个是要如果说这个时候前端有播报的情况，在用户语音输入的时候要给信号给到 rtc 后端去停止视频和音频流的输出，然后转为静默。
2. 对话接口就是对话接口就好了，在得到 asr 转录的结果之后先返回给前端，然后用户确认转录没有错误发送给对话接口，对话接口得到流式返回文本给前端，前端再把这个流式的文本给到 rtc 客户端，让它去生成视频和音频流

### 时序图

时序图

![[Untitled diagram _ Mermaid Chart-2025-09-24-025219.png]]

```
sequenceDiagram
  autonumber
  participant User as User
  participant App as 前端(采集/UI/控制)
  participant AIN as ASR Ingest
  participant MinIO as MinIO
  participant Qwen as Qwen-Audio API
  participant ASR as ASR 编排
  participant ORCH as Dialog 接口
  participant LLM as LLM/Dify
  participant RTC as RTC(文本→TTS/Avatar)
  participant Player as 播放器

  %% 阶段A：用户开口 + 静默控制
  User->>App: 开始说话
  App->>RTC: 控制: setMute(true)/pause()（静默）
  App->>AIN: 推送音频分片(WS/GRPC)

  %% 阶段B：ASR 路径（落盘→URL→Qwen）
  AIN->>MinIO: 写入分片/合并文件
  AIN-->>ASR: 文件就绪事件(含对象信息)
  ASR->>MinIO: 生成可访问URL（签名/代理）
  ASR->>Qwen: 传 URL 调用转写
  Qwen-->>ASR: 转写文本(候选/最终)
  ASR-->>App: 返回转写结果（带置信度/时间戳等）

  %% 阶段C：前端确认再入对话
  App->>User: 显示转写结果，等待确认
  User-->>App: 点“确认发送”
  App->>ORCH: 发送最终文本（含会话态）

  %% 阶段D：对话流式返回（先到前端，再转RTC）
  ORCH->>LLM: Prompt/上下文（可串 Dify 工具）
  LLM-->>ORCH: 逐字/逐句文本流
  ORCH-->>App: 流式文本
  App->>RTC: 转发文本流（最小延迟）

  par TTS
    RTC-->>Player: 音频帧(流)
  and Avatar
    RTC-->>Player: 视频帧(流)
  end

  %% 阶段E：用户说完，恢复播放
  App-->>RTC: 控制: setMute(false)/resume()
  Player-->>User: 播放 TTS + Avatar

  rect rgba(220,220,220,0.18)
  note over App,RTC: 任何时刻再次拾音：<br/>前端立即下发静默信号给 RTC，<br/>暂停/静音当前播报（barge-in）。
  end
```
